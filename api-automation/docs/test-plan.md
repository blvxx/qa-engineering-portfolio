# Test Plan — JSONPlaceholder Posts API

## 1. Objective

Verify the observable HTTP contract of the Posts resource and its relationship with Comments. The project covers positive, negative, CRUD, schema and isolated API-client unit scenarios.

## 2. System under test

- Base URL: `https://jsonplaceholder.typicode.com`
- Main resource: `/posts`
- Related resource: `/posts/{id}/comments`
- API format: JSON over HTTP
- Authentication: not required by the demo service

## 3. Scope

### In scope

| Area | Checks |
|---|---|
| Read collection | `GET /posts`, status, content type, collection type and expected number of records |
| Read resource | `GET /posts/{id}`, valid IDs, required properties and response schema |
| Filtering | `GET /posts?userId={id}`, result ownership and empty results for unknown users |
| Relationships | `GET /posts/{id}/comments`, parent-child relationship and comment schema |
| Create | `POST /posts`, valid request body, `201 Created`, generated ID and response fields |
| Replace | `PUT /posts/{id}`, full replacement request and response representation |
| Partial update | `PATCH /posts/{id}`, partial payload and returned resource representation |
| Delete | `DELETE /posts/{id}`, successful HTTP response |
| Client unit behavior | URL construction, headers, query parameters, JSON payloads, timeouts, environment configuration and session cleanup |

### Out of scope

- Authentication and authorization.
- Persistent database changes and transaction handling.
- Load, stress, endurance and performance testing.
- Security, penetration and vulnerability testing.
- Browser UI and end-to-end user journeys.
- Production SLA and availability guarantees.

## 4. Test types and techniques

- Functional testing of supported HTTP methods.
- Positive and negative testing.
- Contract testing with JSON Schema Draft 2020-12.
- Relationship testing for nested Comments.
- Parametrized testing for multiple IDs and user filters.
- Equivalence partitioning for valid and unknown identifiers.
- Boundary-oriented checks for invalid IDs and user filters.
- Unit testing with mocked `requests.Session` objects to isolate client behavior from network availability.

## 5. Test environment

| Component | Configuration |
|---|---|
| Runtime | Python 3.10 and 3.12 in CI |

Local setup and execution commands are described in the [project README](../README.md).

## 6. Test data

| Data class | Values / examples | Expected behavior |
|---|---|---|
| Existing post IDs | `1`, `10`, `50`, `100` | Existing post returned with a valid schema |
| Invalid post IDs | `0`, `-1`, `999999` | `404` response for the direct resource endpoint |
| Existing user IDs | `1`, `2`, `5`, `10` | Returned posts contain the requested `userId` |
| Unknown user IDs | `0`, `999`, `-5` | Empty collection |
| Existing parent posts | `1`, `10`, `100` | Five related comments per post, each with matching `postId` |
| Unknown parent post | `999999` | Empty comments collection |
| Create post payload | `userId`, non-empty `title`, non-empty `body` | `201 Created` and a response containing the submitted fields plus generated ID |
| Invalid create payloads | Missing fields, empty title, out-of-range user ID, unexpected `id` | Rejected by the local request schema validator |

## 7. Entry criteria

- Dependencies are installed from `requirements-dev.txt`.
- The test suite and schema files are available in the repository.
- Public API tests have network access to the configured base URL.

## 8. Exit criteria

- Static checks complete without reported Ruff errors.
- Isolated unit tests pass.
- Live API tests pass, or external-service/network failures are explicitly recorded.
- JUnit and Allure results are generated by CI.
- Any failed assertion is investigated and documented; external API unavailability is not reported as an application defect.

## 9. Risks and limitations

| Risk | Impact | Mitigation / interpretation |
|---|---|---|
| Public demo API unavailable | Live tests cannot complete | Run isolated unit tests separately; rerun live tests when service is reachable |
| Write operations are simulated | CRUD responses do not change stored data | Validate request/response contract only; do not assert persistence |
| Public service behavior may change | Contract assertions can become outdated | Recheck the official service guide before changing expected results |

| Schema validation | `test_post_schema_definition_is_valid`, `test_schema_rejects_invalid_post`, `test_create_request_schema_rejects_invalid_payload` |

## 11. Defect reporting

Each defect report should contain:

1. Title with resource, method and observed issue.
2. Environment and base URL.
3. Preconditions and test data.
4. Reproduction steps and exact request.
5. Expected result and actual result.
6. HTTP status, response headers and response body.
7. Severity, priority and evidence (sanitized request/response or Allure attachment).
